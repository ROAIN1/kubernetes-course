# Part A — Linux

## A1. Processes and systemd

### What is it?
- A **process** is a running program. It has a **PID** (process ID), an owner (user), memory, and open files.
- **PID 1** is the first process. It starts all others and cleans up dead children.
- **systemd** is the PID 1 on most Linux servers (RHEL, Oracle Linux, Ubuntu). It starts and watches **services** (also called **units**).
- **journald** stores service logs. You read them with `journalctl`.

### Why do we need it for Kubernetes?
On every Kubernetes node, the **kubelet** (the node agent) and **containerd** (the container runtime) run as systemd services. When a node goes `NotReady`, the first checks are `systemctl status kubelet` and `journalctl -u kubelet`. On OKE worker nodes this is exactly what you do over SSH.

### How it works
```
PID 1: systemd
 ├── containerd.service   → starts container processes (your pods)
 │     └── containerd-shim → nginx (PID 4321)  ← a container is just a process
 ├── kubelet.service      → talks to API server, asks containerd to run pods
 └── sshd.service
```
A container is **not** a small VM. It is a normal Linux process with extra isolation (see A2).

### Real production scenario
Your OKE worker node shows `NotReady`. Pods on it are being evicted. You SSH to the node. `systemctl status kubelet` says `failed`. `journalctl -u kubelet -n 50` shows `failed to load kubelet config file`. Someone edited the config. You fix it and run `systemctl restart kubelet`. The node becomes `Ready`.

|---|---|---|

## A2. Namespaces and cgroups — what a container really is

### What is it?
- A **namespace** changes what a process can **see**. Types: `pid` (process list), `net` (network interfaces, IPs, routes), `mnt` (filesystems), `uts` (hostname), `ipc`, `user`, `cgroup`.
- A **cgroup** (control group) limits what a process can **use**: CPU, memory, disk I/O, number of processes.

**Container = process + namespaces (isolation) + cgroups (limits) + a filesystem image.**

### Why do we need it?
Without namespaces, every app sees every other app's processes and ports. Without cgroups, one app with a memory leak can use all RAM and crash the whole server.

### How it works internally
```
          Linux kernel
   ┌──────────────────────────────────────────┐
   │  cgroup: memory.max = 256Mi, cpu.max = ½ │  ← limits (Kubernetes "limits")
   │  ┌───────────── namespaces ────────────┐ │
   │  │ pid: sees only its own processes    │ │
   │  │ net: own eth0, own IP, own ports    │ │  ← isolation
   │  │ mnt: own root filesystem (image)    │ │
   │  │ uts: own hostname                   │ │
   │  │      process: nginx (PID 1 inside)  │ │
   │  └─────────────────────────────────────┘ │
   └──────────────────────────────────────────┘
```

**Kubernetes link:**
- A **Pod** = a group of containers that **share** the `net` namespace (same IP, talk over `localhost`) and can share volumes.
- `resources.limits.memory` in a pod becomes a cgroup `memory.max`. Use more → the kernel kills the process → Kubernetes shows **OOMKilled**.
- `resources.limits.cpu` becomes `cpu.max`. Use more → the process is **throttled** (slowed), not killed.

### Real production scenario
A Laravel app on your cluster restarts every 20 minutes. `kubectl describe pod` shows `Last State: Terminated, Reason: OOMKilled, Exit Code: 137`. The memory limit is 256Mi but a report job needs 400Mi. You raise the limit and fix the job's memory use. Now you know: 137 = 128 + 9 (signal 9, SIGKILL from the kernel OOM killer).

# Part B — Networking

## B1. TCP/IP, IP addresses, ports, and routing

### What is it?
- **IP address** — the address of a network interface, e.g. `10.0.1.15`.
- **CIDR** — a range of addresses. `10.0.0.0/16` = first 16 bits fixed = 65,536 addresses. `/24` = 256 addresses.
- **Port** — a number (0–65535) that picks one program on a host. HTTP = 80, HTTPS = 443, SSH = 22, DNS = 53.
- **TCP** — reliable, ordered, connection-based (3-way handshake: SYN, SYN-ACK, ACK). Used by HTTP, databases.
- **UDP** — no connection, no retransmit, fast. Used by DNS, VXLAN overlays, metrics.
- **Route** — a rule: "to reach network X, send packets to gateway Y via interface Z". The **default route** (`0.0.0.0/0`) is used when nothing else matches.

### Why do we need it for Kubernetes?
A Kubernetes cluster has **three** IP ranges. They must never overlap with each other or with your VCN:

```
 Node network   e.g. 10.0.10.0/24   (OCI VCN subnet for worker nodes)
 Pod network    e.g. 10.244.0.0/16  (every pod gets an IP from here)
 Service network e.g. 10.96.0.0/16  (virtual IPs for Services — not on any interface)
```
On OKE with **VCN-Native Pod Networking**, pods get real IPs from a VCN subnet. With **Flannel**, pods use an overlay range. Planning these CIDRs badly is a classic cause of "cluster can't reach the database".

### How a packet travels
```
 App → socket (dst 10.0.20.5:3306, TCP)
   → kernel looks up route table → "10.0.20.0/24 via 10.0.10.1 dev eth0"
   → sends to gateway → router → DB host → port 3306 → MySQL process
```

### Real production scenario
A new OKE cluster cannot reach an on-premises database over the VPN. `ip route` on the node is fine. You find the pod CIDR `10.244.0.0/16` overlaps the on-prem range `10.244.8.0/24`. Return traffic goes to the wrong place. The fix: rebuild with a non-overlapping pod CIDR. Lesson: plan CIDRs before building.

## B2. DNS

### What is it?
**DNS** (Domain Name System) turns names into IP addresses. Record types you must know:
- **A** — name → IPv4 address. **AAAA** — name → IPv6.
- **CNAME** — name → another name (alias).
- **SRV** — name → host + port (Kubernetes creates these for Services).
- **TTL** — how long a resolver may cache the answer.

### Why do we need it?
Apps should use names, not IPs, because IPs change. In Kubernetes, pods get new IPs every time they restart. **CoreDNS** gives every Service a name like `orders.shop.svc.cluster.local`. DNS problems are among the top causes of "the app cannot connect".

### How it works
```
 app: connect to "orders"
   → libc reads /etc/resolv.conf
        nameserver 10.96.0.10              ← CoreDNS Service IP
        search shop.svc.cluster.local svc.cluster.local cluster.local
        options ndots:5
   → tries orders.shop.svc.cluster.local  → CoreDNS answers 10.96.45.12
```
`ndots:5` means: a name with fewer than 5 dots is tried with each `search` suffix first. That is why `api.example.com` from a pod can cause several extra DNS queries.

### Real production scenario
After a migration, an app on OKE cannot reach `db-prod.internal.example`. From your laptop it resolves. From the pod, `nslookup` fails. The private DNS zone is only attached to the old VCN's resolver. You add a forwarding rule in CoreDNS (or attach the private view to the new VCN resolver). The app connects.

### Troubleshooting

| Symptom | Cause | Check / fix |
|---|---|---|
| `could not resolve host` | Wrong nameserver, DNS down, typo | `cat /etc/resolv.conf`, `dig <name>`, `dig @<other-server> <name>` |

| Slow external lookups from pods | `ndots:5` causes many search queries | Use FQDN with a trailing dot (`api.example.com.`) or tune `dnsConfig` |

## B3. HTTP, HTTPS, and TLS

### What is it?
- **HTTP** — a text protocol: request (method, path, headers, body) → response (status code, headers, body).
- Status codes: **2xx** OK, **3xx** redirect, **4xx** client error (404 not found, 403 forbidden), **5xx** server error (502 bad gateway, 503 unavailable, 504 gateway timeout).
- **HTTPS** = HTTP inside **TLS**. TLS encrypts traffic and proves the server identity with a **certificate**.
- A **certificate** has a subject name (and SANs, Subject Alternative Names), a validity period, and is signed by a **CA** (Certificate Authority). Clients trust a chain: server cert → intermediate CA → root CA.
- **SNI** (Server Name Indication) — the client sends the host name in the TLS handshake, so one IP can serve many certificates. Ingress controllers depend on this.

### Why do we need it?
Ingress controllers terminate TLS. cert-manager renews certificates. Expired certificates and wrong SANs are classic outages. Knowing 502 vs 503 vs 504 tells you *where* a request failed.

### How it works
```
 Client                         Server (e.g. Ingress controller)
   │── TCP handshake ─────────────►│
   │── ClientHello (SNI=shop.example.com) ─►│
   │◄─ ServerHello + certificate chain ─────│
   │   client checks: name matches? not expired? trusted CA?
   │── key exchange, encrypted from here ──►│
   │── GET /api/orders  Host: shop.example.com ─►│
   │◄─ HTTP/1.1 200 OK ─────────────│
```

### Real production scenario
Monday 09:00. Users get "Your connection is not private". `openssl s_client` shows `notAfter` was yesterday. The certificate was renewed by hand last year and nobody set a reminder. The fix today: install a new certificate. The fix forever: cert-manager with automatic renewal, plus an alert 21 days before expiry.

## B4. Firewalls and load balancing

### What is it?
- A **firewall** allows or blocks packets by source, destination, port, and protocol. On Linux, **iptables** / **nftables** do this in the kernel (netfilter). On OCI: **security lists** (per subnet) and **NSGs** (per VNIC).
- A **load balancer** spreads requests across many backends. **L4** works with TCP/UDP (IP + port). **L7** understands HTTP (host, path, headers) and can terminate TLS.
- **Health checks** remove dead backends from rotation.

### Why do we need it?
- **kube-proxy** programs iptables (or IPVS) rules on every node. That is how a Service IP reaches pods. A Service *is* firewall/NAT rules.
- A Service of type **LoadBalancer** on OKE creates an **OCI Load Balancer** or **Network Load Balancer**.
- An **Ingress controller** is an L7 load balancer inside the cluster.

### How it works
```
           ┌──────── L7 load balancer (nginx) ────────┐
 client ──►│ Host: shop → round robin, health checks  │
           └──────┬───────────────┬───────────────────┘
                  ▼               ▼
              backend-1       backend-2      (if one dies, health check removes it)
```

### Real production scenario
After a security hardening change, the OKE nodes stop reaching the API server. The new NSG blocks TCP 6443 from the worker subnet. Pods keep running, but nodes go `NotReady` and nothing new can be scheduled. Restoring the rule fixes it. Lesson: know the ports Kubernetes needs (6443 API, 10250 kubelet, 12250 on OKE for worker-to-control-plane, NodePorts 30000–32767).

### Hands-on lab 1: a firewall rule with iptables

# Part C — Containers with Docker

## C1. Images, layers, containers, and registries

### What is it?
- **Image** — a read-only package: a filesystem (in **layers**) + metadata (default command, env, ports). Identified by `name:tag` and a **digest** (`sha256:...`, which never changes).
- **Layer** — one filesystem change (from one Dockerfile instruction). Layers are shared and cached.
- **Container** — a running instance of an image + a thin **writable layer** on top.
- **Registry** — a server that stores images: Docker Hub, OCI Container Registry (OCIR, e.g. `me-jeddah-1.ocir.io`), GHCR, ACR, ECR.

### Why do we need it?
Kubernetes never builds code. It only **pulls images** and runs them. Every pod spec says `image: ...`. `ImagePullBackOff` is one of the most common pod errors, and it is almost always about the registry, the tag, or credentials.

### How it works
```
 image nginx:1.27
 ┌────────────────────────────┐
 │ writable layer (container) │ ← lost when container is deleted
 ├────────────────────────────┤
 │ layer 3: nginx config      │  read-only, shared by all
 │ layer 2: nginx binaries    │  containers using this image
 │ layer 1: debian base       │
 └────────────────────────────┘
 pull: registry → node's containerd → unpack layers → start process
```
**Tags can move** (`latest`, even `1.27`). **Digests cannot.** Production deployments should pin a specific version tag, and ideally a digest.

### Real production scenario
A deployment uses `image: myapp:latest`. A developer pushes a broken build as `latest`. A node restarts, the pod is rescheduled, pulls the new `latest`, and crashes. The other replicas still run the old image. Now replicas run different code. Fix: immutable version tags (`myapp:1.4.2` or git SHA) and `imagePullPolicy: IfNotPresent`.

| No scanning | Image scanning (Trivy, OCIR scanning), signed images (notebook 08) |

## C2. Dockerfiles and multi-stage builds

### What is it?
A **Dockerfile** is a recipe to build an image. Key instructions:
- `FROM` base image · `WORKDIR` working folder · `COPY` files in · `RUN` a build command · `ENV` env var · `EXPOSE` documents a port · `USER` run as this user · `ENTRYPOINT`/`CMD` the start command.

A **multi-stage build** uses several `FROM` stages. Stage 1 has compilers and tools. The final stage copies **only the result**.

### Why do we need it?
- Small images pull faster → pods start faster → faster scaling and recovery.
- Fewer packages = fewer vulnerabilities. A final image with no shell is much harder to attack.
- Running as a non-root `USER` is required by Kubernetes Pod Security "restricted" (notebook 08).

### How it works
```
 Stage "build"  (golang:1.22-alpine, ~250 MB)
   COPY source → go build → /out/app (single static binary)
               │ COPY --from=build
               ▼
 Final stage  (distroless/static:nonroot, ~2 MB) + app (~7 MB)  → ~10 MB image
```

### Real production scenario
Your team's Node.js image is 1.2 GB. Autoscaling adds nodes during a traffic spike, but new pods take 3 minutes to start because each node pulls 1.2 GB. A security scan finds 300 CVEs, mostly in build tools nobody uses at runtime. A multi-stage build cuts it to 150 MB and 10 CVEs. Pods now start in 20 seconds.

## C3. Container networking

### What is it?
- **bridge** (default) — containers get private IPs on a virtual switch (`docker0`). Outbound traffic is NATed through the host.
- **user-defined bridge** — like bridge, plus **DNS by container name** (you saw this in B2).
- **host** — container uses the host's network namespace directly.
- **none** — no network.
- **Port publishing** `-p host:container` — a NAT rule from host port to container port.
- Containers can **join another container's network namespace** (`--network container:<name>`). This is exactly how a Kubernetes **Pod** works.

### Why do we need it?
Kubernetes replaces Docker networking with a **CNI plugin**, but the ideas are the same: veth pairs, bridges, NAT, DNS by name. The "shared network namespace" trick is the reason containers in one pod can talk over `localhost`.

### How it works
```
 Host
  eth0 (host IP) ── NAT (-p 8080:80) ──┐
  docker0 / br-xxx bridge  172.18.0.1  │
     ├── veth ── container A  172.18.0.2:80
     └── veth ── container B  172.18.0.3
                  └── container C (--network container:B) shares B's IP & ports
                        = like 2 containers in one Pod
```

### Real production scenario
A team runs an app container and a log-shipper sidecar. The sidecar must read metrics from the app at `localhost:9090`. In Docker they are separate, so `localhost` fails. In Kubernetes they put both in **one pod**. They share the network namespace, so `localhost:9090` works. Understanding this saves hours.

### Hands-on lab

##CODE
%%bash

### Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Containers cannot resolve each other by name | Using default `bridge` network (no DNS) | Use a user-defined network |
| `port is already allocated` | Host port in use | Choose another host port |

| Two containers in a pod fail: `address already in use` | Both bind the same port in a shared namespace | Use different ports per container |

The `127.0.0.1` vs `0.0.0.0` mistake is very common in Kubernetes too: the pod is Running, but the Service gets "connection refused".

### Lab vs Production

| Lab | Production (Kubernetes) |
|---|---|
| Docker bridge + NAT | CNI plugin (OCI VCN-Native, Flannel, Calico, Cilium): every pod gets a routable IP |
| `-p` port publishing | Services, Ingress, cloud load balancers |
| Name DNS from Docker | CoreDNS Service names |

## C4. Volumes and storage

### What is it?
- The container writable layer is **temporary**: deleted with the container.
- A **named volume** — storage managed by Docker, survives container deletion.
- A **bind mount** — a host folder mounted into the container.
- **tmpfs** — in-memory storage, gone at stop.

### Why do we need it?
Databases, uploads, and caches need data that survives restarts. In Kubernetes the same idea becomes **volumes**, **PersistentVolumes**, and **PersistentVolumeClaims** (notebook 05). On OKE, a PVC can create an **OCI Block Volume** automatically.

### How it works
```
 container  /var/lib/mysql ──mount──► named volume "dbdata"  (outside the container's layers)
 delete container → volume stays → new container mounts it → data is back
```

### Real production scenario
A team runs MySQL in a container "for a quick test". It becomes important. One day someone runs `docker rm -f` to restart it. All data is gone — it lived in the writable layer. With a volume (or, in Kubernetes, a PVC on block storage plus backups), the data would have survived.

### Hands-on lab

##CODE
%%bash

echo "== Write data into a named volume, then delete the container =="

echo "== New container, same volume: data survives =="

echo "== Without a volume: data is lost =="

### Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Data lost after restart | No volume; data in writable layer | Mount a volume / PVC |
| `permission denied` on mounted folder | UID in container ≠ owner of files | Match UID, `chown`, or `fsGroup` in Kubernetes |
| Bind mount empty on Mac | Folder not shared with the VM | Use paths under your home folder (shared by default) |
| DB corrupted after copying volume while running | Copied files during writes | Use DB-native backup (mysqldump, snapshots with quiesce) |

### Lab vs Production

| Lab | Production |
|---|---|
| Named volume on laptop disk | PVC on OCI Block Volume (CSI), replicated storage, snapshots |
| No backups | Scheduled backups (Commvault, Velero, DB dumps) + **tested restores** |
| One container | StatefulSet with stable storage per replica |

## Interview and real-world questions

1. "Explain what a container is to someone who knows VMs."
2. "A pod restarts with exit code 137. What happened and how do you confirm it?"
3. "A user says the website is down. Walk me through how you narrow it down from DNS to the app."
4. "Why should production images be small and run as non-root?"
5. "Your image works on your MacBook but fails on the OKE nodes with `exec format error`. Why?"
6. "What is the difference between a security list and an NSG on OCI, and how does that relate to Kubernetes NetworkPolicy?"

<details><summary>Answers</summary>

1. A VM virtualises hardware and runs its own kernel. A container shares the host kernel. It is a process isolated with namespaces (what it sees) and limited with cgroups (what it uses), running from an image filesystem. So containers start in milliseconds and use less memory, but isolation is weaker than a VM.
2. 137 = 128 + 9 = SIGKILL, usually the kernel OOM killer because the container exceeded its memory limit. Confirm with `kubectl describe pod` (`Last State: Terminated, Reason: OOMKilled`) and `kubectl top pod`, and look at memory metrics before the restart.
3. DNS: `dig site` → correct IP? Network: `curl -v` → connect OK or timeout/refused? TLS: certificate valid? HTTP: status code — 502/503/504 point to the backend layer. Then the load balancer health, Ingress logs, Service endpoints, pod readiness, app logs. Move from outside to inside, one layer at a time.
4. Small images pull faster (faster scaling and recovery) and contain fewer packages, so fewer vulnerabilities. Non-root limits damage if the app is compromised and is required by restricted Pod Security.
5. The Mac builds arm64 images by default. Many node pools are amd64. Build for the target platform with `docker buildx build --platform linux/amd64` (or multi-arch).
6. A security list applies to all VNICs in a subnet. An NSG applies to specific VNICs (resources) and can reference other NSGs. Both work at the VCN level. A NetworkPolicy works inside the cluster, between pods, using labels. Production uses both layers.
</details>

## Practical assignment

**Scenario:** The Events team gives you a Python web app. They want a production-quality container image before it goes to Kubernetes.

**Tasks**
1. Create `labs/01/pyapp/app.py`: a web server on port 8000 that returns `events ok` on `/` (use Python's `http.server`, no extra packages).
2. Write a Dockerfile that:
   - uses `python:3.12-alpine`,
   - runs as a non-root user,
   - sets env `PYTHONUNBUFFERED=1` (logs appear immediately),
   - starts the app.
3. Build it as `events-api:0.1.0`. Run it with a **128 MiB memory limit** and **0.5 CPU**, published on host port 8090.
4. Prove: it responds, runs as non-root, and the cgroup memory limit is 134217728.
5. Push it to a local registry on port 5001 as `localhost:5001/events/events-api:0.1.0`.

**Success criteria:** `curl localhost:8090` returns `events ok`; `docker exec ... id -u` is not `0`; `memory.max` shows 134217728; the registry catalog lists `events/events-api`.

**Hints:** `adduser -D -u 10001 app` on Alpine; `USER 10001`; `docker run -m 128m --cpus 0.5`.

<details><summary>Solution</summary>

```bash
mkdir -p labs/01/pyapp && cd labs/01/pyapp
cat > app.py <<'EOF'
from http.server import BaseHTTPRequestHandler, HTTPServer

class H(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"events ok\n")

HTTPServer(("0.0.0.0", 8000), H).serve_forever()   # 0.0.0.0, not 127.0.0.1
EOF
cat > Dockerfile <<'EOF'
FROM python:3.12-alpine
ENV PYTHONUNBUFFERED=1
RUN adduser -D -u 10001 app
WORKDIR /app
COPY app.py .
USER 10001
EXPOSE 8000
CMD ["python", "app.py"]
EOF
docker build -t events-api:0.1.0 .
docker run -d --name events -m 128m --cpus 0.5 -p 8090:8000 events-api:0.1.0
sleep 1
curl -s localhost:8090                                  # events ok
docker exec events id -u                                # 10001
docker exec events cat /sys/fs/cgroup/memory.max        # 134217728
docker run -d --rm --name registry -p 5001:5000 registry:2
docker tag events-api:0.1.0 localhost:5001/events/events-api:0.1.0
docker push localhost:5001/events/events-api:0.1.0
curl -s localhost:5001/v2/_catalog                      # {"repositories":["events/events-api"]}
docker rm -f events registry
```
</details>

## Break it challenge

This Dockerfile builds, but the container is **unreachable** from the host, the image is **huge**, and every code change **re-downloads all dependencies**. Find all three problems.

```dockerfile
FROM golang:1.22
WORKDIR /src
COPY . .
RUN go mod download
RUN go build -o /app .
CMD ["/app", "--listen", "127.0.0.1:8080"]
```
Run with: `docker run -p 8080:8080 badapp` → `curl localhost:8080` fails.

<details><summary>Solution</summary>

1. **Unreachable:** the app listens on `127.0.0.1` inside the container. Port publishing sends traffic to the container's `eth0` IP, not loopback. Listen on `0.0.0.0:8080` (or `:8080`).
2. **Huge image:** single stage based on the full `golang` image (~800 MB). Use a multi-stage build with a distroless or alpine final stage.
3. **No dependency cache:** `COPY . .` comes before `go mod download`, so any code change invalidates the download layer. Copy `go.mod`/`go.sum` first, download, then copy the code.

Bonus problem: it runs as **root**. Add a non-root `USER`.
</details>
